## Что сказать в начале

«Я использовал проект с треугольниками из первой лабораторной и разделил
обязанности между классами. Controller получает стороны, ищет результат в
SQLite, при отсутствии записи вычисляет и сохраняет его. Затем отправляет
строку-результат имитации сервера и возвращает её. Повторный запрос использует
готовую запись. В тестах пользователь и сервер заменены заглушками».

## Что открыть преподавателю

1. `controller.py` — основной сценарий, четыре шага отмечены комментариями.
2. `database.py` — методы `add`, `get`, `delete`, составной ключ из трёх сторон.
3. `interfaces.py` — абстрактные классы `UserInput` и `ResultSender`.
4. `tests/test_integration.py` — первые три теста нового запроса, кэша и повтора.
5. `main.py` — создание компонентов и запуск.

## Назначение классов

| Класс | Ответственность |
| --- | --- |
| `TriangleCalculator` | Вызывает `classify_triangle` из предыдущей лабораторной |
| `TriangleDatabase` | Сохраняет, получает и удаляет запись SQLite |
| `ConsoleInput` | Реализует интерфейс `UserInput`, читает три строки через `input()` |
| `SimulatedSender` | Реализует интерфейс `ResultSender`, имитирует отправку выводом строки |
| `Controller` | Определяет порядок взаимодействия остальных классов |

## Что означают основные строки

- `record = self.database.get(*sides)` — найти запись по трём сторонам;
  `*sides` передаёт три элемента кортежа как три аргумента метода.
- `if record is None` — если записи нет, требуется вычисление.
- `self.database.add(...)` — сохранить тип и сообщение об ошибке.
- `self.sender.send_result(message)` — отправить итоговую строку.
- `return message` — вернуть ту же строку вызывающему коду.
- `PRIMARY KEY (side_a, side_b, side_c)` — одна запись на конкретную тройку строк.
- `?` в SQL — передать значения отдельно от текста запроса.
- `with self.connection` — подтвердить транзакцию при успехе, отменить при ошибке.
- `finally: database.close()` — закрыть соединение, даже если сценарий прервётся.

Ключ сохраняет порядок и текст сторон: `3, 4, 5` и `5, 4, 3` — разные ключи;
`3` и `3.0` — разные входные строки. Пробелы по краям убирает `ConsoleInput`.
Ошибочный ввод также сохраняется с сообщением об ошибке и может браться из кэша.
Координаты вычисляются старым методом, но сценарий ЛР3 хранит в БД только пять
полей, требуемых заданием, и отправляет строку типа/ошибки.

## Как объяснить интеграционный тест

«Юнит-тест проверяет отдельный компонент. Интеграционный тест проверяет
совместную работу нескольких настоящих компонентов. В моих тестах настоящие
Controller, калькулятор и SQLite. Заглушки заменяют ввод и сервер, чтобы тест
не требовал ручного ввода и сети».

В `setUp()` создаётся новая БД `:memory:` для каждого теста.
`self.addCleanup(self.database.close)` освобождает соединение после теста.
`create_autospec` создаёт заглушку по интерфейсу. `Mock(wraps=...)` вызывает
настоящий калькулятор и позволяет подсчитать вызовы.

В тесте кэша `calculate.assert_not_called()` доказывает, что вычисление
не повторялось. В тесте повтора калькулятор вызван один раз, отправка — дважды.
Тест удаления показывает, что после удаления записи контроллер считает заново.

## Короткие ответы на вопросы

**Зачем нужен Controller?** Чтобы логика порядка действий была в одном месте.

**Почему SQLite?** Она встроена в Python, работает с обычным файлом и не требует
установки отдельного сервера.

**Что такое ABC?** Абстрактный базовый класс. Он задаёт обязательные методы
интерфейса; создать объект самого интерфейса нельзя.

**Зачем заглушки?** Чтобы тесты были автоматическими и не зависели от пользователя
и доступности стороннего сервера.

**Отправляются ли настоящие письма/запросы?** В задании предусмотрена имитация.
`SimulatedSender` печатает сообщение, а в тестах его заменяет заглушка.

**Что при сбое отправки?** Сохранённый результат остаётся в БД. Ошибка отправки
передаётся вызывающему коду; повторный запрос использует кэш.

**Что при сбое БД?** Сценарий прекращается с исключением до отправки.

**Чем эти тесты отличаются от ЛР2?** ЛР2 проверяла математику. Здесь проверяются
кэш, сохранение, удаление, ввод, отправка и взаимодействие компонентов.

**Что означает 100% покрытия?** В тестах выполнены все учитываемые строки
и ветвления прикладного кода. Это не доказывает отсутствие любых возможных
ошибок; это проверка полноты выполнения кода для выбранных сценариев.
